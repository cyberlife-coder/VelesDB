# tauri-plugin-velesdb examples

A Tauri plugin is never a standalone program: it is registered in a host app.
So each example here is the **set of files you drop into a Tauri 2 project**,
not a binary you run from this directory.

| Example | What it gives you |
|---|---|
| [`quickstart/`](./quickstart) | The smallest complete app that talks to VelesDB: plugin registration, the capability that unlocks the commands, and a frontend that creates a collection, upserts two points and searches. Raw `invoke` — no npm dependency beyond `@tauri-apps/api`. |
| [`production-config/`](./production-config) | The same app configured the way you would actually ship it: per-user app-data directory, a `velesdb.toml` that fails fast, and the `Builder` that wires them together. |
| [`graph-and-memory/`](./graph-and-memory) | Beyond vectors: knowledge-graph edges and traversal, the three agent-memory families, and collection events — plus the two Rust-side workarounds you need because some paths have no IPC command. |

## Prerequisites, shared by all three

| Requirement | Minimum | Note |
|---|---|---|
| Rust | 1.90 | workspace `rust-version` |
| Tauri | 2.11 | the plugin builds against `tauri = "2.11"` |
| Node.js | 18 | frontend toolchain only |
| A Tauri 2 project | — | starting from zero? [Tauri RAG tutorial](../../../docs/tutorials/tauri-rag-app/README.md) |
| Platform toolchain | — | Xcode CLT on macOS, `libwebkit2gtk-4.1-dev` and friends on Linux, nothing extra on Windows |

Add the plugin from your app's `src-tauri/` directory:

```bash
cargo add tauri-plugin-velesdb
```

The optional typed frontend wrapper is a separate package — the raw `invoke`
calls used in these examples need no extra dependency:

```bash
npm install @wiscale/tauri-plugin-velesdb
```

## The three things that trip everyone up

**1. Commands are denied until a capability allows them.** Tauri 2 gates every
plugin command. Without `src-tauri/capabilities/velesdb.json`, `invoke` rejects
before the request ever reaches the plugin. Every example ships that file.

**2. The IPC layer is `camelCase`; the REST server is `snake_case`.** The
request field is `topK` here and `top_k` over HTTP. Same engine, two
conventions, because each matches its own ecosystem.

**3. Every request carries its own `collection` field.** There is no URL path
in IPC, so the collection that the REST API takes from
`/collections/{name}/search` is a field in the request body instead. The one
exception is `query`: its target comes from the `FROM` clause or the `MATCH`
pattern inside the VelesQL string, and any extra `collection` field is silently
dropped.

## Error shape

Every rejection is a `{ message, code }` object:

```js
try {
  await invoke('plugin:velesdb|search', { request });
} catch (e) {
  console.error(e.code, e.message);   // e.g. "VELES-002", "Collection 'x' not found"
}
```

| Code | Meaning |
|---|---|
| `VELES-001` | the collection already exists |
| `VELES-002` | the collection was not found — check the name, it is case-sensitive |
| `VELES-004` | vector dimension mismatch |
| `INVALID_CONFIG` | wrong collection family, or a VelesQL parse error |

A permission error that fires *before* reaching the plugin means the capability
is missing, or `windows` does not list the calling window's label.
