# Mobile build guide (iOS / Android)

How to turn the [`velesdb-mobile`](../../crates/velesdb-mobile/README.md) crate into
something an Xcode or Gradle project can consume: cross-compiled libraries plus the
Swift/Kotlin bindings generated by [UniFFI](https://mozilla.github.io/uniffi-rs/).

> **Verification status.** The host build and the binding generation below were run
> against this repository and produce exactly the output shown. The iOS packaging
> (`lipo`, `xcodebuild -create-xcframework`) and the Android `cargo-ndk` steps are the
> documented procedure — they mirror `crates/velesdb-mobile/src/lib.rs` and
> [INSTALLATION.md](./INSTALLATION.md) — but **no workflow in this repository builds or
> tests them**. Validate them on your own device matrix.

## 1. Toolchain

```bash
# iOS targets (macOS host required)
rustup target add aarch64-apple-ios        # device
rustup target add aarch64-apple-ios-sim    # simulator, Apple silicon
rustup target add x86_64-apple-ios         # simulator, Intel

# Android targets
rustup target add aarch64-linux-android    # ARM64 devices
rustup target add armv7-linux-androideabi  # ARMv7 devices
rustup target add x86_64-linux-android     # x86_64 emulator
rustup target add i686-linux-android       # x86 emulator (declared, never exercised here)

# Android: NDK-aware cargo wrapper
cargo install cargo-ndk
```

`crates/velesdb-mobile/Cargo.toml` declares
`crate-type = ["cdylib", "staticlib", "lib"]`, so a single build produces the static
library iOS wants (`.a`), the shared library Android wants (`.so`), and the Rust
`rlib`/dylib used by host tooling.

## 2. Generate the bindings (host build, no device needed)

The bindgen entry point is a normal binary in the crate
(`src/bin/uniffi-bindgen.rs`, `uniffi::uniffi_bindgen_main()`), run in **library
mode**: it reads the compiled library and emits the foreign-language sources.

```bash
cargo build -p velesdb-mobile
cargo run -p velesdb-mobile --bin uniffi-bindgen -- generate \
    --library target/debug/libvelesdb_mobile.dylib \
    --language swift \
    --out-dir bindings/swift
```

The `--library` file is the host artifact: `libvelesdb_mobile.dylib` on macOS,
`libvelesdb_mobile.so` on Linux, `velesdb_mobile.dll` on Windows. Use
`target/release/...` after a `--release` build.

Swift output (three files, verified):

```text
bindings/swift/velesdb_mobile.swift
bindings/swift/velesdb_mobileFFI.h
bindings/swift/velesdb_mobileFFI.modulemap
```

Kotlin output (one file, verified):

```text
bindings/kotlin/uniffi/velesdb_mobile/velesdb_mobile.kt
```

Naming consequences you cannot change without repackaging:

| Aspect | Value | Source |
|---|---|---|
| UniFFI namespace | `velesdb_mobile` | `uniffi::setup_scaffolding!()` in `src/lib.rs`, derived from the crate name |
| Kotlin package | `uniffi.velesdb_mobile` | `package` line of the generated `.kt` |
| JNA library name | `velesdb_mobile` → `libvelesdb_mobile.so` | `Native.register(..., "velesdb_mobile")` in the generated `.kt` |
| Swift module | the framework you build | Swift has no package declaration; the module is the framework name (`import VelesDB` in the samples) |

For a **device** build, generate from the cross-compiled artifact instead — e.g.
`--library target/aarch64-apple-ios/release/libvelesdb_mobile.a` or
`--library target/aarch64-linux-android/release/libvelesdb_mobile.so`. The generated
sources are identical across targets; only the linked binary differs.

## 3. iOS: static libraries and XCFramework

```bash
cargo build --release --target aarch64-apple-ios -p velesdb-mobile
cargo build --release --target aarch64-apple-ios-sim -p velesdb-mobile
cargo build --release --target x86_64-apple-ios -p velesdb-mobile

# One fat simulator slice (a single XCFramework slice cannot hold two archs
# for the same platform variant otherwise).
mkdir -p target/universal-sim
lipo -create \
    target/aarch64-apple-ios-sim/release/libvelesdb_mobile.a \
    target/x86_64-apple-ios/release/libvelesdb_mobile.a \
    -output target/universal-sim/libvelesdb_mobile.a

xcodebuild -create-xcframework \
    -library target/aarch64-apple-ios/release/libvelesdb_mobile.a \
    -headers bindings/swift \
    -library target/universal-sim/libvelesdb_mobile.a \
    -headers bindings/swift \
    -output VelesDB.xcframework
```

Then add `VelesDB.xcframework` to the Xcode target and add
`bindings/swift/velesdb_mobile.swift` to the app's sources (it is plain Swift that
calls the C ABI declared in `velesdb_mobileFFI.h`).

Unverified on current toolchain: `xcodebuild -create-xcframework` expects the
directory passed to `-headers` to expose a module map under the name it looks for;
UniFFI emits `velesdb_mobileFFI.modulemap` (see
`crates/velesdb-mobile/examples/generate_bindings.sh`), so a rename to
`module.modulemap` inside the headers directory may be required. This step has not
been executed in this repository — check the `xcodebuild` output on your machine
before assuming the layout above is complete.

## 4. Android: shared libraries, jniLibs, JNA

```bash
cargo ndk -t arm64-v8a -t armeabi-v7a -t x86_64 \
    build --release -p velesdb-mobile
```

Artifacts land in the usual per-target directories:

```text
target/aarch64-linux-android/release/libvelesdb_mobile.so
target/armv7-linux-androideabi/release/libvelesdb_mobile.so
target/x86_64-linux-android/release/libvelesdb_mobile.so
```

Package them under the ABI names the Android runtime expects:

```text
app/src/main/jniLibs/arm64-v8a/libvelesdb_mobile.so
app/src/main/jniLibs/armeabi-v7a/libvelesdb_mobile.so
app/src/main/jniLibs/x86_64/libvelesdb_mobile.so
```

`cargo-ndk`'s `-o <dir>` flag writes that layout directly (unverified on current
toolchain — confirm with your `cargo-ndk` version: `cargo ndk -o app/src/main/jniLibs
-t arm64-v8a build --release -p velesdb-mobile`).

Two Gradle-side requirements come from the generated Kotlin itself:

- It imports `com.sun.jna.*`, so the app must depend on JNA — the Android build needs
  the `@aar` flavour of the artifact, not the plain JVM jar.
- It declares `package uniffi.velesdb_mobile`; place the file at
  `src/main/kotlin/uniffi/velesdb_mobile/velesdb_mobile.kt` or add its parent
  directory as a source set.

A missing or mismatched ABI surfaces at runtime as `UnsatisfiedLinkError` when JNA
looks for `libvelesdb_mobile.so`.

## 5. Checking the binding without a device

The binding types are plain Rust and the crate's own suite exercises them:

```bash
cargo test -p velesdb-mobile
```

Expected on a host with default features: `123 passed` (lib target), `8 passed`
(`tests/coverage_native.rs`), `4 passed` (`tests/feature_parity.rs`).
`feature_parity.rs` is the guard that fails the build when `velesdb-core` grows a
`DistanceMetric` or `StorageMode` variant that the mobile mirror has not adopted.
