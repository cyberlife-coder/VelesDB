# Building the Node addon from source

> When the prebuilt `@wiscale/velesdb-memory-node` binary does not cover your
> platform — or when you are changing `crates/velesdb-node` itself — this is
> how to compile it locally.

Most users never need this page: `npm install @wiscale/velesdb-memory-node`
downloads a prebuilt `.node` binary for the five supported targets. See
[Compatibility](../../crates/velesdb-node/README.md#compatibility) for the
list.

## When you need a local build

- **musl / Alpine.** No `*-unknown-linux-musl` prebuild is published, so the
  default `node` Docker image (Alpine-based) cannot load the addon. It fails
  at `require` time with `Failed to load native binding`.
- **Any other triple** — FreeBSD, `armv7`, Android, 32-bit Windows.
- **You are working on the binding.** `index.js`, `index.d.ts` and the
  `.node` binary are generated by `napi build` and are git-ignored; a fresh
  checkout has none of them.

There is no automatic source fallback: the loader tries the per-platform
package, then a local `.node` file, then throws. It never invokes a compiler
on your behalf.

## Prerequisites

| Requirement | Minimum version | Note |
|---|---|---|
| Rust | 1.90 | The workspace `rust-version`. Install via [rustup](https://rustup.rs). |
| Node.js | 18.17 | The package `engines.node` floor; CI builds on Node 20. |
| A platform linker and C toolchain | — | Xcode Command Line Tools on macOS, `build-essential` on Debian/Ubuntu, the MSVC "Desktop development with C++" workload on Windows. Rust does not ship a linker. |
| Ollama | any | **Optional.** Only for `embedder: "ollama"` and `rememberExtracted`; the default `hash` embedder needs no model and no network. |

No system VelesDB installation is required: the addon statically links
`velesdb-memory`, which is built from this repository.

## Build

From `crates/velesdb-node`:

```bash
npm install
npx napi build --platform --profile release-node
```

This produces three artifacts next to `package.json`:

| Artifact | What it is |
|---|---|
| `velesdb-memory-node.<platform>.node` | the native addon |
| `index.js` | the loader that picks the right `.node` for the host |
| `index.d.ts` | generated TypeScript types for the whole surface |

The `release-node` profile is not optional. `panic` cannot be overridden in a
per-package profile, so the workspace defines a dedicated profile that
inherits `release` with `panic = "unwind"` — napi's panic→JS-error conversion
depends on unwinding. A plain `--release` build would abort the Node process
instead of rejecting a Promise.

`npm run build` is the same command, and `npm run build:debug` is the
unoptimized variant (fast to compile, slow at runtime).

## Test

```bash
npm test    # node --test __test__/*.spec.mjs
```

The functional suite uses the offline `hash` embedder, so it needs no Ollama
and no network. Two notes on running it:

- `__test__/index.spec.mjs` imports `../index.js` — it fails with a clear
  "run `npm run build` first" message if the addon has not been built.
- `__test__/skills-sync.spec.mjs` is pure Node fs and runs standalone:
  `node --test __test__/skills-sync.spec.mjs` works with no addon at all. It
  guards the skills bundled into the npm package against drift from their
  sources of truth elsewhere in the repo.

## Cross-compiling

Add the target's standard library, then pass the triple explicitly:

```bash
rustup target add aarch64-unknown-linux-gnu
npx napi build --platform --profile release-node \
  --target aarch64-unknown-linux-gnu --use-napi-cross
```

`--use-napi-cross` supplies a zig-based sysroot, so no Docker and no
distribution cross-toolchain is needed. This is exactly what the release
workflow does for the one cross target it builds
(`.github/workflows/release-memory.yml`, job `build-node`); the other four
targets are built natively on their own runner.

## Using a locally built addon in another project

The generated `index.js` resolves the `.node` file next to it, so a plain file
dependency works:

```bash
npm install /absolute/path/to/velesdb/crates/velesdb-node
```

Import it exactly as you would the published package:

```js
import { MemoryService } from '@wiscale/velesdb-memory-node'
```

## Troubleshooting a local build

| Symptom | Cause | Fix |
|---|---|---|
| `Failed to load native binding` after `npm install` from source | `napi build` has not run, so no `.node` file exists yet | run `npx napi build --platform --profile release-node` |
| `index.d.ts not found — run npm run build` from the test suite | same: the generated types are git-ignored | build before testing |
| `linker 'cc' not found` / `link.exe not found` | no C toolchain installed | install Xcode CLT, `build-essential`, or the MSVC C++ workload |
| `error: toolchain '...' does not support target` | the cross target's std is missing | `rustup target add <triple>` for the toolchain cargo actually uses |
| The build succeeds but the process aborts on an internal error | built with `--release` instead of `--profile release-node` | rebuild with `--profile release-node` (`panic = "unwind"`) |
